# fnox setup

The repository pins fnox **v1.50.0**, the current baseline/latest stable reviewed for this setup ([release notes](https://github.com/jdx/fnox/releases/tag/v1.50.0)). This release makes provider-setting resolution failures visible even when `if_missing` is `warn` or `ignore`; run `fnox check --strict` to make warnings fail validation.

## Audit and daemon cache

Both global config variants enable `[audit]`. The local JSON-lines audit records secret names, commands, profiles, providers, and cache status—not values, command lines, or environment contents. fnox creates the log with mode `0600`, but it is **not tamper-proof**: anything running as your account can edit or delete it, and reads outside fnox are not recorded. Keep the default in fnox's state directory (`fnox audit --path` shows the location); for stronger retention, forward it to a separately controlled log collector. [Audit log docs](https://fnox.jdx.dev/guide/audit.html)

The daemon remains enabled with an 8-hour idle timeout. `cache_ttl = "30m"` is sliding (a read restarts it); `max_cache_ttl = "4h"` is absolute. Whichever expires first causes the next read to resolve the provider again, potentially prompting for 1Password/SSO or age identity access. `fnox get --refresh NAME` and `fnox exec --refresh NAME -- ...` can refresh one named value before its TTL; other cached values remain unaffected. These limits reduce cache residency; they do not rotate or revoke a value already read. Use `fnox exec --redact -- ...` only for a command whose piped or redirected output needs protection; terminals are not redacted, and this is not a sandbox. `fnox scan --values` is an optional value-aware check; it resolves configured secrets but only reports matching file paths/names. Do not install a hook unless separately wanted. [Daemon cache](https://fnox.jdx.dev/guide/daemon.html) · [exec redaction](https://fnox.jdx.dev/cli/exec.html) · [scan](https://fnox.jdx.dev/cli/scan.html)

## Files and age identities

Use fnox `[files]` only in the user-level global config and only for a file you explicitly intend to manage as an encrypted secret; do not put machine-local credentials in shared project config. `fnox files write` replaces whatever is at a target path, including a symlink (it does not follow the link). Back up the current target and confirm how to restore it before the first write; removing the fnox entry does not restore overwritten contents. [Files docs](https://fnox.jdx.dev/cli/files.html) · [write behavior](https://fnox.jdx.dev/cli/files/write.html)

In the macOS config, the age provider gets its identity from the OS keychain. If that entry is missing, age-encrypted values cannot bootstrap their own decryption; use an independently available provider or recover the keychain entry first. The existing `SOPS_AGE_KEY_FILE` secret is an explicit 1Password `as_file` reference—preserve it; it is not a request to migrate local files. Named age identities and macOS Touch ID/Secure Enclave are possible future options, not migrations in this change. [Age provider](https://fnox.jdx.dev/providers/age.html) · [Touch ID and sync](https://fnox.jdx.dev/guide/sync.html#touch-id-and-the-daemon)

For a read-only survey of common local credential files, use [`scripts/assess-local-secret-files.ps1`](scripts/assess-local-secret-files.ps1). It reports only paths, statuses, and heuristic indicator classes; it skips recognized `.env`, private-key, and age-identity paths without reading them. Supply only non-key configuration files as additional paths. Findings do not determine whether another file is safe or appropriate to migrate.
